01. Architectural Fundamentals

The Disaggregated Storage Revolution

Traditional databases couple compute and storage onto the same machine, forcing expensive over-provisioning. This system takes a different approach: it decouples compute nodes from durable storage entirely, utilizing cloud object stores (like AWS S3) as the primary persistence tier.

However, S3 brings a challenge: network round-trips take ~50â€“150ms per request. To achieve sub-millisecond database writes and reads, our storage engine employs an in-memory Memtable write-buffer paired with a local SSD read-cache.

02. The Write Path

Memtable Buffering: Turning Random Writes into Sequential I/O

When an application writes to the system, the record lands in an in-memory Memtable sorted by key (implemented as a JavaScript Map, analogous to Rust's BTreeMap). Because RAM access takes ~100 nanoseconds, write operations respond instantaneously.

Buffering writes in memory serves a critical architectural purpose: instead of issuing thousands of slow, random I/O requests to cloud storage, the engine accumulates writes in memory until a threshold is crossed (set to 4 keys in this demo), converting random writes into bulk sequential files.

03. Cloud Persistence

Flushing: Creating Immutable SSTables in Object Storage

When the Memtable reaches capacity, a background worker triggers a Flush. The contents of the Memtable are serialized into a binary, sorted string table (SSTable) and uploaded to the mock Object Store (S3).

These flushed files are strictly immutable. Once written to object storage, they are never modified in place. To ensure fast subsequent access, the newly written SSTable is also populated into the node's local SSD cache. Once durable in S3, the RAM Memtable is safely cleared to receive new writes.

04. The Read Path

Multi-Tier Read Hierarchy: 100ns RAM to 100ms Cloud

Point lookups traverse a strict 3-tier hierarchy: first checking Memtable (~100ns), then Local SSD Cache (~0.5ms), and finally fetching from the Object Store (~95ms) over simulated network HTTP.

Try reading a key after writing it: if it's still in RAM, latency is ~100ns. After a flush, it hits the local SSD cache (~0.5ms). If the local cache is cold or cleared, the probe fetches directly from S3 (~95ms) and lazily caches the SSTable for future queries.

05. Storage Optimization

Compaction: Bounding Read Amplification & Reclaiming Space

As flushes recur, multiple Level 0 SSTables accumulate in Object Storage. Searching across dozens of files increases read amplification. Furthermore, overwrites or deletes leave obsolete key versions occupying paid storage.

Periodically, background Compaction merges multiple Level 0 files into a single Level 1 file. During compaction, key versions are deduplicated (keeping only the newest), reclaiming cloud disk space and bounding read latency.

06. Production Architecture

Stateless Recovery: Disaggregated Engines in Production

In a disaggregated storage engine like this one, compute data-nodes maintain no state that isn't durable in object storage. Click the Simulate Node Crash button above to observe this resilience in action.

When a node crashes, all RAM Memtables and local SSD caches are wiped out. However, because every flushed SSTable lives durably in S3, the new replacement node boots up immediately, serving reads directly from object storage while lazily rebuilding its local SSD cache â€” achieving zero data loss and instant cloud recovery.
